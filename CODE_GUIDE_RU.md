## 4. Какие данные читаются

### Карта

`Map` объявлен в `include/KC_searching.hpp`, реализован в `src/KC_searching.cpp`.

Ищи `read_file_to_cells`, `empty_map`, `in_bounds`, `traversable`. Внутри `cells[i][j] == true` означает препятствие. Координаты в поиске — **строка i, столбец j**, не привычные x,y. В `.scen` координаты x,y; при подготовке задач они уже переставлены.

### Примитивы

`data/base_control_set.txt` читается через `ControlSet::load_primitives`.

У `Primitive` существенны:

- `start_theta`: начальное направление робота;
- `goal`: **относительное** конечное состояние `(delta_i, delta_j, theta_end)`;
- `swept_cells_i`, `swept_cells_j`: дискретный collision trace относительно начала;
- `length`: исходная длина;
- `id`: идентификатор, используемый при восстановлении пути.

Текущий набор: 384 примитива, 24 на каждое из 16 начальных направлений; ID от 384 до 767. Поэтому нельзя считать, что каждый элемент `list_all_prims` ненулевой: в коде регулярно встречается `if (p)`.

`ControlSet::cost(id)` возвращает `float`. Для наших доказательств и проверок используем именно эту стоимость, переведённую в double, а не повторно вычисленную аналитическую длину кривой. Но накопление g/f в поиске остаётся float — это отдельный источник численных расхождений.

`get_prims_by_heading(theta)` возвращает список применимых ID. Направления робота: 0 вправо, 4 вниз, 8 влево, 12 вверх; промежуточные номера не надо автоматически трактовать как равномерную сетку углов.

### Mesh-таблицы

`data/base_mesh_info.txt` читается через `MeshInfo::load`.

Ключевые поля:

| Поле | Смысл |
|---|---|
| `successors[config]` | Переходы `(di, dj, next_config, prim_id)` из конфигурации |
| `initial_config_by_theta` | Какая initial-конфигурация соответствует lattice-направлению |
| `theta_by_initial_config` | Обратное отображение; для внутренней конфигурации −1 |
| `primitives_in_config[config]` | Возможные завершения: конечное направление, смещение до конца, индекс текущей клетки в следе, ID примитива |

В `Vertex` поля `theta` и `config_id` находятся в `union`: один слот означает направление в lattice-графе либо номер конфигурации в mesh-графе. Нельзя трактовать `config_id` внутреннего Mesh-узла как направление робота.

## 5. Общий цикл A*

Открой `include/KC_astar.hpp`. Алгоритм шаблонный: один и тот же цикл работает с `StateLatticeParams` или `MeshGraphParams`.

`AstarSearch(params, lazy)`:

1. Создаёт стартовый узел: g=0, f=h(start).
2. Пока OPEN не пуст, вызывает `StepAstar` и увеличивает `step_count`.
3. Возвращает цель либо результат «OPEN исчерпан».

`StepAstar` извлекает узел, при Lazy-режиме проверяет отложенную коллизию, проверяет цель, генерирует соседей, добавляет их в OPEN и отмечает текущий узел в CLOSED.

Поэтому `steps` — число итераций внешнего цикла. Внутри извлечения могут отбрасываться дубликаты/устаревшие узлы; последняя итерация также может только исчерпать очередь. Нельзя без уточнения подписывать этот счётчик «число уникальных раскрытых состояний».

Цикл не обязан знать, что такое примитив или конфигурация: это спрятано за методами `params`.

### OPEN, CLOSED и best-g

В `src/KC_searching.cpp`:

- `NodeCompare` сравнивает f; отдельного явно заданного предпочтения по g при равном f нет.
- `SearchTree::add_to_open` учитывает кандидата и при включённом best-g отбрасывает путь, не улучшающий сохранённое g.
- `get_best_node_from_open` отбрасывает закрытые и, при best-g, устаревшие записи.
- `add_to_closed` выставляет бит и решает, сохранять ли сам узел в памяти.
- `state_index` переводит `(i,j,layer)` в индекс. Layer — theta для lattice и config для Mesh.

`compact_closed` выделяет битовый массив по фактической карте и числу слоёв. Это улучшение структуры данных, не новая эвристика. `best_g` — отдельный эксперимент: на LBA* помогал, на MeshA* общего выигрыша не дал. В основной измеренной серии best-g выключен; для h=0 эталона включён. Это не реализация повторного раскрытия CLOSED. Для LazyLBA* best-g отключается, чтобы ещё не проверенный на коллизию дешёвый путь не подавил допустимый более дорогой.

`MyHEAP` — пул памяти, **не очередь с приоритетами**. OPEN — другая структура. Указатели `ptrSearchNode` и `ptrVertex` хранят индексы в пуле. Глобальный `HEAP` и static-буфер соседей делают текущую реализацию непригодной для независимых параллельных поисков в разных потоках без переработки.

## 6. Где LBA* отличается от MeshA*

Оба графа реализованы в `src/KC_search_params.cpp`.

### LBA*

Смотри `StateLatticeParams::get_successors`:

1. Из текущего theta выбираются применимые примитивы.
2. Относительное смещение переводится в координаты карты.
3. `check_primitive` проверяет клетки collision trace; для Lazy это откладывается.
4. Конечное состояние получает `g_new = g_current + c(p)`.
5. `heuristic` вызывает нашу lattice-оценку, после чего получается f.

### MeshA*

Смотри `MeshGraphParams::get_successors`, `mesh_set_parent`, `mesh_should_prune`.

Поиск идёт по состояниям `(i,j,config)`. Общие части следов разных примитивов представлены совместно. Внутренние переходы имеют нулевую стоимость, полная c(p) начисляется при завершении примитива. Initial-конфигурация означает точку стыковки примитивов, а не обязательно начало всего поиска. Граф в целом циклический, с одним OPEN.

В текущем коде есть дополнительная ветка: если у внутреннего узла осталось единственное подходящее завершение, проверяется оставшийся след и создаётся переход прямо к нему. Перед действующей функцией лежит большой закомментированный вариант — при чтении не перепутай его с исполняемым кодом.

`mesh_set_parent` сохраняет связь с нужной initial-вершиной, поэтому промежуточные узлы можно освобождать, не теряя последовательность примитивов для восстановления.

### Самое важное место подключения эвристики

В том же файле найдёшь `static inline float base_heuristic(...)`.

- Для initial-узла вызывается `lattice_heuristic->value(i,j,theta)`.
- Для внутреннего узла перебираются возможные концы и берётся минимум `c(p) + h_LBA(endpoint)`.

Почему полная c(p), хотя узел уже внутри следа? Потому что внутренние нулевые рёбра ещё не начислили эту стоимость в g.

Реализация дополнительно исключает заблокированные и CLOSED-концы. Это динамическая логика поиска. Доказательство согласованности статической lattice-оценки нельзя автоматически выдавать за доказательство всей этой реализации с отсечениями и float.

## 7. Где собраны наши эвристики

Объявления — `include/KC_heuristic.hpp`. Основной класс — `LatticeHeuristic`; ключевой метод — `value(i,j,heading)`.

Режим выбирается `HeuristicMode`; строку CLI преобразует `parse_heuristic_mode`, обратное имя возвращает `heuristic_mode_name`.

| Режим | Невзвешенная оценка при точной цели | Основное место |
|---|---|---|
| `euclidean` | Исходная Euclid | Старый путь в search params; также ветка в `value` |
| `safe-euclidean` | beta · Euclid | `KC_heuristic.cpp` |
| `grid` | alpha · d_grid | Там же |
| `max` | max(beta · Euclid, alpha · d_grid) | Там же |
| `kinematic` | max(spatial, h_kin) | `KC_heuristic.cpp` + `KC_kinematic.cpp` |
| `additive` | max(сохранённая spatial-база, alpha · d_grid + h_res) | Те же файлы, другие веса таблицы |
| `directional` | max(spatial, направленные потенциалы) | `KC_heuristic.cpp` + `KC_directional.hpp` |

`spatial` обычно означает `max(beta * Euclid, 0.9 * d_grid)`. Параметр alpha доступен отдельно; additive намеренно сохраняет базу 0.9, даже когда испытывается меньшая доля стоимости для сложения.

`--weight` — отдельный множитель w в поиске. Он не равен alpha или beta. Все наши утверждения о согласованности относятся к невзвешенной h; в основной серии w=1. При w=0 возвращается ноль без вычисления `0 * infinity`.

## 8. Калибровка alpha и beta

Открой `src/KC_heuristic.cpp`: функция `trace_distance`, затем конструктор `HeuristicCalibration`.

Для примитива p берётся множество клеток его следа T_p. `trace_distance` запускает Дейкстру **в графе, индуцированном этим множеством**, между началом и концом. Соседи — 8 клеток, веса 1 и sqrt(2).

Полученное D_p — не длина списка collision trace: между клетками множества разрешены сокращения. Если примитив допустим на карте, весь сдвинутый T_p свободен, поэтому `d_grid(start,end) <= D_p`.

Калибровка проверяет весь конечный набор:

```text
alpha_limit = min_p c(p) / D_p
beta_limit  = min_p c(p) / ||delta(p)||
```

Для текущего control set:

- alpha_limit = 0.9025533755561258; используем alpha=0.9.
- beta_limit = 0.9933301598151829; код округляет вниз до beta=0.9933.
- Ограничивающий grid-примитив — 760.

Alpha — не эмпирическая подгонка по задачам. Она согласует grid-метрику с ценой примитивов. Beta учитывает, что цена некоторых заданных примитивов чуть меньше расстояния между центрами их дискретных концов. Это разные поправки.

Из треугольника и ограничения alpha:

```text
alpha * d_grid(s,G)
  <= alpha * d_grid(s,t) + alpha * d_grid(t,G)
  <= c(p) + alpha * d_grid(t,G).
```

Максимум двух согласованных оценок также согласован. Произвольное сложение — нет. Выпуклая комбинация не превосходит максимум поточечно; если её коэффициент зависит от состояния, согласованность требует отдельного доказательства. Такая комбинация сейчас не реализована.

## 9. Обратная Дейкстра и grid-поле

В конструкторе `LatticeHeuristic`:

1. `distances_` заполняется бесконечностями.
2. Целевая клетка получает ноль и попадает в очередь. Для допустимых режимов с областью цели источников несколько.
3. Выполняется Дейкстра по свободным клеткам карты.
4. `grid_distance(i,j)` становится доступом к массиву за O(1).

Heading при этом забывается. Диагональ требует свободных концов; запрета прохода между двумя заблокированными боковыми клетками здесь нет. Это намеренное расслабление, согласованное с использованным доказательством.

Поле строится один раз **на solve**, а не при каждом вызове h. В текущем полном benchmark оно не переиспользуется между вариантами или повторами. Его стоимость входит в `end_to_end_s` и отдельно записывается в `grid_s`.

Ответ на старый вопрос «Дейкстра быстрее MeshA*?»: сравниваем весь `подготовка grid + поиск с улучшенной h + прочие этапы solve` с полным solve базового варианта. Само поле считается на более простом двумерном графе. Выигрыш возможен, когда сокращение поиска окупает подготовку; на простых задачах подготовка может сделать вариант медленнее.

## 10. Кинематическая таблица

Файлы: `include/KC_kinematic.hpp`, `src/KC_kinematic.cpp`.

Состояния абстрактного графа:

```text
q = ((i-i_G) mod P, (j-j_G) mod P, theta)
q_G = (0, 0, theta_G)
```

Препятствий нет, координаты циклические. Примитив сохраняет начальный/конечный heading, смещение по модулю P и стоимость. Это конечное расслабление настоящего lattice-графа, не точное расстояние на бесконечной свободной плоскости.

В конструкторе:

- `transitions` собирает переходы из control set;
- `incoming` группирует их по конечному heading;
- обратная Дейкстра идёт от `q_G`;
- координаты предшественника вычисляются **вычитанием** смещения примитива;
- `wrap` исправляет отрицательный остаток C++.

Обращение рёбер для Дейкстры не означает, что робот получил возможность физически ехать задом.

`value(di,dj,theta)` индексирует готовую таблицу. `compatible` проверяет, что внешний кэш соответствует периоду, целевому heading, переходам и весам. Таблица не зависит от карты или абсолютной позиции цели, но зависит от theta_G.

Размер расстояний — `P * P * 16 * sizeof(double)`: P=64 даёт 0.5 MiB, P=256 — 8 MiB на целевое направление. При P1, делящем P2, более подробный фактор-граф даёт не более слабую оценку; для произвольных периодов такое сравнение не обещается.

Кэш и холодная подготовка — разные эксперименты. Основной runner не реализует межзапросный кэш кинематических таблиц; старые соответствующие эксперименты находятся в `tools/kinematic_experiment.cpp` и `tools/multimap_experiment.cpp`.

## 11. Аддитивная оценка и разделение стоимости

Смотри `HeuristicCalibration::residual_costs(alpha)` и ветки `HeuristicMode::Additive` в `KC_heuristic.cpp`.

Стоимость примитива делится:

```text
c(p) = alpha * D_p + r_alpha(p),
r_alpha(p) = c(p) - alpha * D_p >= 0.
```

Периодическая таблица строится по остаточным весам r_alpha. Поэтому можно складывать `alpha * d_grid + h_res`: обе части используют разные доли одного бюджета стоимости.

Затем берётся максимум с сохранённой spatial-базой. Для нашего набора при alpha<=0.9 это

```text
max(beta * Euclid, 0.9 * d_grid, alpha * d_grid + h_res).
```

Отрицательные остатки не обрезаются молча до нуля: это скрывало бы нарушение бюджета. Код отвергает такой параметр. Для таблицы с другим alpha кэш не совместим.

Этот подход мы реализовали и проверили, но убедительного общего выигрыша времени не получили. Перебор alpha лежит в `tools/alpha_experiment.cpp`; выводы — в `res/alpha-experiment/REPORT.md`.

## 12. Направленная оценка

Вся базовая реализация — структура `DirectionalPotential` в `include/KC_directional.hpp`.

Здесь нужно различать:

- a,b,theta — направления **робота**, вершины графа из 16 состояний;
- v — фиксированное **пространственное направление проекции**. Их тоже 16, но это другая сетка, равномерная по углу.

Для каждого v:

```text
r_v(p) = c(p) - beta * <v, delta(p)> >= 0
```

Примитив даёт ребро `theta_start -> theta_end` с весом r_v. Из нескольких рёбер между двумя heading оставляем минимальное. Массив `d[v][a][b]` сначала содержит эти рёбра и нули на диагонали, затем три вложенных цикла Флойда вычисляют D_v(a,b).

В `value`:

```text
h_v(s) = beta * <v, x_G-x_s> + D_v(theta_s,theta_G)
h_dir(s) = max(0, max_v h_v(s))
```

А `LatticeHeuristic::value` возвращает `max(spatial, h_dir)`.

Почему это нижняя оценка: на реальном пути сумма проекций телескопируется в проекцию общего смещения, а сумма остаточных весов не меньше кратчайшего пути в графе heading. Почему согласована: D_v удовлетворяет неравенству кратчайшего пути на каждом ребре. Семейство v фиксировано на весь поиск; максимум сохраняет свойство.

Стоимость таблиц расстояний — 16×16×16 doubles, то есть 32 KiB. На один вызов h перебираются 16 проекций. Оценка может сильно уменьшить поиск на отдельных задачах, но затраты на вычисление и сильное grid-поле иногда съедают выигрыш.

### Непустое продолжение: новая ветка

Кандидат находится **только** в `res/directional-nonempty/source/include/KC_directional.hpp`.

Обычная таблица допускает пустой путь: D_v(a,a)=0. Если s ещё не цель, реальное решение содержит хотя бы один примитив. Поэтому используем

```text
D_v^+(a,b) = min_{p: theta_start=a} [r_v(p) + D_v(theta_end,b)].
```

При a!=b таблица не меняется. Для a=b требуется непустой цикл, который может иметь положительную остаточную стоимость. Новые диагональные элементы сначала вычисляются по старой таблице, затем записываются все вместе. В точной целевой позе `value` отдельно возвращает ноль.

Полное объяснение, доказательство, проверки и числа — `res/directional-nonempty/REPORT.md`. На старых 24 задачах цены совпали с базовой направленной оценкой во всех 48 запусках. Суммарные итерации среди решённых задач снизились примерно на 0.4% у обоих алгоритмов; общий эффект небольшой. Ускорение времени пока не установлено.

`candidate.patch` — патч кандидата. Не применяй его к копии активного большого прогона.

## 13. Кто создаёт эвристику и что входит во время

Открой `SearchAlgorithm::solve` в `src/KC_algorithms.cpp`.

Порядок: создание `LatticeHeuristic`, создание контекста нужного графа, `AstarSearch`, восстановление пути, сбор счётчиков, удаление контекста и эвристики.

| Поле worker | Что измеряет |
|---|---|
| `end_to_end_s` | Весь solve, включая подготовку, контекст, поиск, восстановление и очистку |
| `preprocessing_s` | Подготовку эвристики |
| `calibration_s`, `grid_s`, `directional_s` | Части подготовки; уже входят в preprocessing |
| `search_s` | Вызов AstarSearch |
| `setup_s`, `cleanup_s` | Создание/удаление контекста и соответствующих структур |
| `reconstruction_s` | Восстановление пути |
| `load_s`, `warmup_s`, `validation_s` | Загрузку, прогрев, проверку пути — вне solve |
| `process_wall_s` | Время жизни отдельного процесса запроса со стороны Python |

Старое поле `total_runtime` включает подготовку, поиск и восстановление, но не все этапы `end_to_end_time`. В строке журнала runner напечатано **process wall time**, а не только `search_s` или `end_to_end_s`.

Не складывай preprocessing с grid и calibration ещё раз: получится двойной учёт.

## 16. Как устроен запуск тестов

### Worker: один запрос

`tools/benchmark_worker.cpp` получает:

```text
MAP ENGINE HEURISTIC si sj st gi gj gt WARMUP
```

ENGINE — `LBA` или `Mesh`; `h0` зарезервирован для LBA-эталона. Worker загружает данные, при WARMUP=1 делает фиксированный маленький прогрев, выполняет один solve, проверяет путь и печатает JSON. Диагностика идёт в stderr. Проверяются следы, стыковка направлений, конечная поза, сумма стоимостей.

Для ручного запроса после большого прогона:

```sh
make -f benchmark.mk
./build-benchmark/benchmark_worker maps/Moscow_0_512.map Mesh directional 120 50 0 300 180 4 1
```

### Runner: очередь и воспроизводимость

`tools/run_benchmark.py` сначала строит h=0 эталоны, затем выполняет выбранные варианты с воспроизводимым перемешиванием задач и сочетаний алгоритм/эвристика внутри каждого повтора.

Эталон: LBA, w=0, best-g=true. Измеренные варианты: LBA/Mesh, w=1, compact CLOSED, best-g=false; `safe-euclidean`, `max`, `directional`; три повтора.

По умолчанию лимит 30 секунд всего процесса измеренного запроса, 120 секунд эталона. Тайм-аут уничтожает группу процесса; это не вывод о недостижимости. Ограничителя памяти нет, RSS только записывается.

Каждый завершённый job немедленно добавляется в JSONL. Resume проверяет хеши, настройки, окружение и пропускает уже записанные job, в том числе ошибки и тайм-ауты. Изменить лимиты и «продолжить тот же опыт» нельзя — нужна новая выходная папка.

### Команды для новой отдельной серии

Выполнять после завершения текущей, в новых выходных папках:

```sh
python3 tools/prepare_final_benchmark.py --verify
make -f benchmark.mk
python3 tools/run_benchmark.py --suite edge --repeats 1 --out results/my-edge
python3 tools/run_benchmark.py --suite pilot --repeats 3 --out results/my-pilot
python3 tools/export_benchmark.py results/my-pilot
```

Размеры этих серий: edge — 64 эталона + 64×2×3 = 448 записей; pilot — 24 эталона + 24×2×3×3 = 456.

Полная серия на всех восьми картах одной командой:

```sh
python3 tools/run_benchmark.py --suite full --repeats 3 --out results/my-full
```

Либо отдельные карты, но с базой и всеми сравниваемыми вариантами на той же машине:

```sh
python3 tools/run_benchmark.py --suite full --maps Berlin_2_256,Milan_1_256 --repeats 3 --out results/my-cities
```

Не запускай эти команды сейчас рядом с уже работающим supervisor. Они создают дополнительную серию, а не показывают состояние существующей.

### Старый CLI

Для изучения одного запроса и текстовых результатов:

```sh
make mesh_astar

./mesh_astar --mode single --map maps/Moscow_0_512.map \

```

`single` выполняет **три** алгоритма: LazyLBA*, LBA*, MeshA*. Результаты — `result_LazyLBAstar.txt`, `result_LBAstar.txt`, `result_MeshAstar.txt`.

Режим `--mode benchmark` из `src/KC_testing.cpp` — старый fork-benchmark с конфигурацией в исходнике. Сейчас для сравнений используем новый Python-runner. Не путай эти два механизма. По умолчанию CLI всё ещё выбирает исходную `euclidean`, поэтому нужную эвристику указывай явно.

## 18. Как разбирать invalid_path и другие статусы

Физический путь проверяет worker; сравнение с эталоном выполняет `verdict` в `run_benchmark.py`.

| Поле/метка | Значение |
|---|---|
| `trace_ok` | Стыковка направлений и клетки следа допустимы |
| `endpoint_ok` | Конечная поза совпадает с заданной |
| `sum_ok` | Сумма стоимостей примитивов в double отличается от накопленного g не более чем на 0.001 |
| `invalid_path` | Не прошла одна из проверок найденного пути; нужно смотреть три поля выше |
| `cost_mismatch` | Проверенный результат расходится по стоимости с проверенным h=0 эталоном |
| `reference_unknown` | Эталон не завершился или не прошёл проверку; нельзя подтвердить стоимость относительно него |
| `reachability_mismatch` | Завершённые результаты алгоритма и эталона расходятся по достижимости |
| `not_completed` | Запрос завершился тайм-аутом/ошибкой, сравнение результата недоступно |

На срезе 11:58 МСК было 45 `invalid_path`, у всех `trace_ok=true` и `endpoint_ok=true`; не прошла численная проверка суммы. Это не 45 столкновений робота. ## 21. Как безопасно добавить свою эвристику

Типовой маршрут для отдельной экспериментальной копии:

1. Добавить режим в `HeuristicMode`, парсер и имя режима.
2. Реализовать подготовку и `value` в `LatticeHeuristic` или отдельном классе.
3. Явно определить допустимые параметры цели, ориентацию и зависимости кэша.
4. Проверить `h(G)=0`, допустимость/согласованность на примитивах, поведение при недостижимости, сохранение baseline при `max`.
5. Сравнить маленькие поиски с h=0, включая восстановленный путь, а не только поле `cost`.
6. Для Mesh использовать существующий перенос через `base_heuristic`. Отдельно учитывать ограничения динамических отсечений.
7. Добавить учёт подготовки в `solve`, если появилась новая фаза.
8. Запустить общие постановки в новой папке и зафиксировать исходники/сборку.

Не изменяй эталон h=0 ради улучшения тестируемого метода. Если требуется исправление общей арифметики или поиска, это новая общая версия и отдельная проверка обеих сторон сравнения.

## 22. Что остаётся сделать с результатами

Текущий supervisor только выполняет серии и пишет служебные сводки. Он не создаст сам окончательные научные графики и выводы.

После завершения:

1. Проверить полноту, тайм-ауты, статусы, стоимость и повторяемость счётчиков.
2. Разобрать численные invalid_path отдельно от геометрических ошибок.
3. Учесть интервал параллельной проверки кандидата из `res/directional-nonempty/interference.json`: 97 завершившихся тогда запусков и следующую запись. Их время не включать в итог как чистые измерения; при необходимости повторить. Не оставлять несопоставимые пары только с одной хорошей стороной.
4. Сравнивать варианты на одинаковых постановках и отдельно показывать решённые, исчерпанные и незавершённые случаи.
5. Экспортировать таблицы и построить графики полного времени, итераций и распределения ускорений по картам/группам.

Сырые CSV можно получить так — пути здесь относятся к корню основной рабочей копии:

```sh
python3 tools/export_benchmark.py res/full-run-2026-10-27/mesha-team-benchmark/results/full-paper
python3 tools/export_benchmark.py res/full-run-2026-10-27/mesha-team-benchmark/results/full-extension
```

Вторую команду выполняй, когда соответствующий журнал существует. Это экспорт строк, включая неуспехи, а не готовая очищенная сравнительная таблица.

Главный результат для защиты — какая эвристика уменьшает **полное время** на каких задачах и почему. Снижение числа итераций помогает объяснить механизм, но само по себе не доказывает ускорение.
