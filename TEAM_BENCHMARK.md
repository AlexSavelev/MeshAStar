# Общие тесты MeshA*: инструкция для команды

Этот комплект содержит исходники планировщика, все восемь карт с `.scen`, примитивы, mesh-данные, 960 заранее выбранных запросов, 64 синтетических случая и изолированный runner. Интернет, Python-пакеты и чужие скомпилированные бинарники не нужны.

Распакуйте в отдельную папку. Не накладывайте архив на рабочую копию своего проекта. Это самодостаточный снимок нашей исследовательской версии: исходная Git-ревизия скачанного проекта неизвестна, поэтому универсальный patch к версии каждого участника был бы ненадёжен. Лицензия оригинального проекта сохранена в LICENSE.txt.

## 1. Сборка и первый запуск

Нужны Python 3.9+, make и компилятор C++11 (GCC или Clang). Поддерживаемые среды: Linux, macOS; на Windows используйте WSL. Из корня распакованного комплекта:

```sh
python3 tools/prepare_final_benchmark.py --verify
make -f benchmark.mk -j4
python3 tests/benchmark_runner_tests.py
python3 tools/run_benchmark.py --suite edge --repeats 1 --out results/edge
python3 tools/run_benchmark.py --suite pilot --repeats 3 --out results/pilot
python3 tools/export_benchmark.py results/pilot
```

Команды ниже предполагают успешно закончившуюся сборку. Для выбора компилятора: `make -f benchmark.mk CXX=g++ -j4`. Если меняете флаги, соберите в чистой копии и передайте runner `--build-label` с фактической командой. `benchmark.mk` собирает только нужный worker, без старых экспериментальных программ. Исходные C++ тесты находятся в tests; полный оригинальный набор запускается через `make test`.

Каждый рабочий процесс сначала загружает входы, выполняет фиксированный маленький прогрев 32×32, затем решает ровно один измеренный запрос с новым полем эвристики. Прогрев не является повторением измеренной задачи. Время загрузки/прогрева/проверки записывается отдельно. Все поиски последовательны; не запускайте несколько runner одновременно на одном компьютере для сравнения времени.

## 2. Какие задачи выполняем

| Группа | Карта | Размер, столбцы × строки | Запросов |
|---|---|---|---:|
| Статья | Labyrinth | 768 × 1024 | 120 |
| Статья | ht_0_hightown | 514 × 514 | 120 |
| Статья | Moscow_0_512 | 512 × 512 | 120 |
| Статья | AR0304SR | 512 × 512 | 120 |
| Дополнение | Berlin_2_256 | 256 × 256 | 120 |
| Дополнение | Milan_1_256 | 256 × 256 | 120 |
| Дополнение | AR0700SR | 320 × 320 | 120 |
| Дополнение | WheelofWar | 768 × 768 | 120 |

`res/final-benchmark-v1/manifest.json` — источник всех постановок. `tasks.tsv` содержит 960 запросов, `pilot.tsv` — 24 заранее выбранных (по одному из каждой трети каждой карты), `edge-tasks.tsv` — 64 краевых. Формат TSV совместим с разбиением по пробельным символам:

```text
task_id map_path start_i start_j start_heading goal_i goal_j goal_heading
```

Координаты — **строка i, столбец j**, не x,y! В исходных `.scen` координаты x,y, преобразование уже выполнено. Heading: 0 вправо, 4 вниз, 8 влево, 12 вверх; всего 16. Параметры цели: точная клетка и ориентация, R=A=0, w=1.

На карте 40 коротких, 40 средних, 40 длинных запросов по третям рангов исходной scenario-длины. Это НЕ классификация по измеренной сложности. В каждой трети 10 пар одинаковых heading, 10 противоположных, 20 других; каждый целевой heading встречается 7 или 8 раз на карте. Seed 2026102601. Ранее исследованные геометрические пары исключены. Достижимость решётки примитивов при отборе не проверялась: невозможные запросы остаются в серии.

Краевые семьи (каждая по 8): идентичная поза; одна клетка и другая ориентация; короткий свободный путь; движения у четырёх границ; одноклеточный коридор; стена с проходом шириной 1; шириной 3; непрерывная стена. Только для идентичной позы заранее требуем стоимость 0, для непрерывной стены — недостижимость. Узкий проход для клеточного агента не гарантирует проходимость для нашего робота.

Восемь карт — расширенная проверка, не независимый ML holdout. Не меняйте выбранные задачи после просмотра своих результатов.

## 3. Полная серия и разделение работы между участниками

Основные варианты: `safe-euclidean`, `max`, `directional`; алгоритмы `LBA`, `Mesh`; три повтора. Это 17 280 измеренных запросов плюс 960 h=0 эталонов. Перед полной серией посмотрите на пилот и ресурсы своей машины. Пример полной серии:

```sh
python3 tools/run_benchmark.py --suite full --repeats 3 --out results/full
```

Можно поделить работу по картам. Важно: на каждой машине прогоняется **и база, и все сравниваемые улучшения**, а не «один участник база, другой улучшение».

```sh
python3 tools/run_benchmark.py --suite full --maps Berlin_2_256,Milan_1_256 --repeats 3 --out results/cities
```

Исходная немасштабированная евклидова эвристика — отдельная контрольная серия, у неё возможна ошибка стоимости относительно эталона:

```sh
python3 tools/run_benchmark.py --suite full --variants euclidean --repeats 3 --out results/raw-euclidean
```

Не смешивайте секунды разных компьютеров в одну сумму «ускорения». Показывайте парные отношения внутри машины/запроса, карту и среду; фиксируйте пересечение завершённых и проверенных задач. Число повторов измеряет шум времени, не увеличивает число независимых задач.

## 4. Тайм-ауты, память и продолжение после остановки

По умолчанию 30 секунд wall time **всего процесса запроса**, включая загрузку, прогрев, solve и проверку; для h=0 — 120 секунд. На тайм-ауте завершается вся группа дочернего процесса. Это не внутрипоисковый лимит; на успешных запросах основная метрика — отдельно измеренный `end_to_end_s`. Лимит памяти не установлен: `peak_rss_bytes` — максимум RSS процесса, а не ограничение. На небольших машинах следите за памятью; смерть от ОС будет `error`, не «нет пути».

Лимиты изменяются только явно, например `--timeout 60 --reference-timeout 180`, в новой выходной папке. Это другая конфигурация; для честного сравнения она должна быть одинаковой у всех вариантов. Не повышайте лимит только выигрышному методу.

Статусы:

- `solved`: найден путь;
- `exhausted_unreachable`: поиск завершился исчерпанием OPEN;
- `timeout`: процесс превысил лимит, достижимость неизвестна;
- `error`: ошибка процесса, сигнал, неподдержанный/испорченный ответ.

Runner сохраняет каждую законченную запись немедленно. Повторите **ту же команду** для продолжения: завершённые job_id (включая ошибки и тайм-ауты) пропускаются, уже учтённые эталоны используются снова. Ctrl+C завершает текущего worker; незавершённый запрос будет запущен снова. Одновременная запись двумя runner в одну папку запрещена. Изменение кода, бинарника, конфигурации или машины запрещает resume; нужна новая папка. Если питание пропало посередине записи JSONL, сначала сохраните копию и восстановите последнюю неполную строку вручную: runner её молча не удаляет.

## 5. Корректность

Эталон на каждом запросе: LBA*, h=0, best-g включён, вне основной временной сводки. В измеренных вариантах best-g выключен, compact CLOSED одинаков. LazyLBA* не входит в эту серию.

Для найденного пути worker проверяет ID/стыковку примитивов, все клетки следа, точную конечную позу и стоимость. В рабочей версии после численного аудита 27 октября используется `cost_validation=float-replay-v1`: последовательность float-сложений по восстановленному пути должна точно воспроизвести сообщённое g. `path_cost_double` отдельно суммирует те же цены примитивов в double; именно эти суммы runner сравнивает с эталоном при допуске 0.001. Исходные g/f поиска остаются float. `legacy_sum_ok` сохраняет результат старой проверки abs(double_sum-float_g)<=0.001. `cost_mismatch` сохраняется как контрпример; допуск сравнения путей не увеличен.

Замороженный комплект от 26 октября и завершившийся большой прогон использовали старую проверку и не изменялись. Для их численного аудита есть `tools/revalidate_path_costs.py`: он создаёт отдельные производные журналы в `res/numeric-validation-2026-10-27`, сохраняя исходные метки. Новую сборку нельзя использовать для resume старого прогона: хеши изменились. Старые строки без маркера float-replay-v1 runner сравнивает по прежней семантике.

`reference_unknown` означает, что h=0 не завершился или не прошёл проверку. Геометрическая допустимость пути всё равно проверяется, но утверждать оптимальность нельзя. `path_valid` на нерешённой задаче не является независимым доказательством недостижимости. У расхождений по достижимости статус `reachability_mismatch`.

## 6. Результаты и что прислать обратно

В выходной папке:

- `metadata.json`: задачи/настройки, хеши исходников и бинарника, ОС/архитектура/машина, метка сборки;
- `runs.jsonl`: одна запись на reference или измеренный запрос; включая неуспехи;
- `logs/`: stdout/stderr каждого процесса;
- `summary.json`: статусы, ошибки, суммарное и медианное время завершённых запусков, пиковая память, несовпадения счётчиков между повторами;
- `results.csv`: создаётся командой экспорта, содержит все исходы и этапы.

В архиве есть `PACKAGE_SHA256.json` с контрольными суммами исходников и входов. В `validation/` лежат наши демонстрационные результаты edge/pilot; это примеры, не папки для resume (имя машины в них удалено).

Присылайте всю выходную папку архивом, свою версию компилятора (`c++ --version`), команду сборки и описание своей модификации. Имя компьютера записывается в metadata: если не хотите его передавать, отредактируйте копию для отправки, а не текущую папку resume.

`end_to_end_s` включает подготовку h, создание поискового контекста, поиск, восстановление и очистку. `preprocessing_s` уже включает `grid_s`, `calibration_s`, `directional_s` — эти поля нельзя складывать второй раз. `steps` — исходные итерации алгоритма, не строго количество раскрытий. `peak_rss_bytes` включает загрузку/пул/прогрев и процесс в целом. `process_wall_s` включает всё, а не только solve. Тайм-аутам не присваиваем время solve=30: оно неизвестно.

Не удаляйте медленные/нерешаемые задачи. Сумма времён только завершённых запросов не является полным временем серии с тайм-аутами. Сравнивать скорость при разных стоимостях найденных путей как «то же решение быстрее» нельзя.

## 7. Как подключить своё улучшение

Лучший вариант — новая отдельная копия этого комплекта: сохраняете карты, постановки и проверки, меняете только свой поиск/эвристику и явно называете метод в результатах. Базу запускаете на той же машине, тем же компилятором и флагами. Простая замена тела существующего режима допустима технически, но в `--build-label` и пояснении обязательно указать, что это ваш метод, а не опубликованный здесь `max`/`directional`. Не объединять такие результаты автоматически по одному имени варианта.

Вход worker: `MAP ENGINE HEURISTIC si sj st gi gj gt WARMUP`. `HEURISTIC=h0` зарезервирован для эталона LBA*; он обязан оставаться неизменным при подключении своего метода. Команда вызывается из корня комплекта. stdout — ровно один JSON schema=1, диагностический вывод — stderr. Ключи и проверка пути реализованы в `tools/benchmark_worker.cpp`; сохраняйте их при адаптации. Для отдельного совместимого бинарника runner принимает `--worker /absolute/path`. Он обязан использовать те же данные, точную цель и единицы времени/стоимости. В метке сборки и присланных исходниках укажите внешнюю реализацию: хеши текущего дерева сами по себе не описывают чужой worker.

Этот runner пока не реализует эксперименты с внешним кэшем кинематических таблиц или ML. Их нельзя имитировать, вычитая время подготовки из холодного запуска: нужен отдельный явный режим и протокол.

## 8. Дополнительная метрика синтетики

По предложению Марата в таблицу со стеной будет добавлено rho=C*_obstacles/C*_free рядом со смещением прохода. Одинаковые позы, примитивы и границы; удаляются только препятствия. Это ось графика для интерпретации, не переключатель эвристик. Ускорение не обязано монотонно расти с rho. Эта диагностическая серия не входит в средние по 960 запросам.

## 9. Версии и история

`res/final-benchmark-v1/PROTOCOL.md` — неизменяемый документ момента фиксации выборки. Его фраза «runner ещё не выполнен» описывает тот момент. Актуальные команды — в этом README, сведения о проведённых проверках — в TEAM_VALIDATION.md. Полная серия из 960 задач автоматически не запускается при распаковке или сборке.
